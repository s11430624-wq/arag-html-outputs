A-RAG: Scaling Agentic Retrieval-Augmented Generation via Hierarchical Retrieval Interfaces

Mingxuan Du et al. · arXiv:2602.03442v1 · February 2026

報告主題

Agentic RAG / LLM 架構
層級化檢索介面 (Hierarchical Retrieval)
多跳開放域問答 (Multi-hop Open-domain QA)
測試時計算量擴展 (Test-time Scaling)

一句話摘要

A-RAG 將 keyword search、semantic search、chunk read 封裝成層級化介面交給 LLM agent，讓模型自己動態決定何時檢索、何時深入讀取證據以及何時給出最終回答。

報告人：吳翊銘
研究所專題討論 · LLM 論文導讀

研究背景：RAG 的角色

RAG 讓 LLM 在回答時能使用外部知識，但檢索策略會決定答案品質。

RAG 解決的問題

  • 顯著降低幻覺 (hallucination)，讓生成內容具有可追溯依據。
  • 補足模型訓練後才出現的即時知識或領域特定私有資料。
  • 適合知識密集型任務，如問答、長篇學術研究及企業智能客服。

但目前 RAG 的瓶頸在於檢索

  • 檢索器的錯誤或不相關資訊會直接污染 LLM context。
  • 一次性取回過多 token 會造成大模型注意力分散並浪費大量算力。
  • 複雜的推理問題通常需要多輪搜尋與逐步尋找實體關聯。

現有方法的核心限制

問題不是只有檢索器不夠強，而是大語言模型沒有被賦予參與檢索決策的權力。
關鍵限制 造成的負面影響 A-RAG 解決方案
Single-shot retrieval 一次性取回固定 Top-k，無法根據中間推理過程調整搜尋方向。 允許 Agent 進行多輪動態搜尋
Predefined workflow 檢索路徑固定。不論面對簡單或複雜的查詢，都執行相同流程。 自主且靈活的動態規劃
Context overload 大量長 chunk 直接塞入 context，帶來極高的 token 成本與雜訊。 先看 Snippet 再決定讀取 Full Chunk
Poor scaling 隨著模型推理能力變強，被動的檢索管道無法發揮其推理優勢。 釋放 Test-time Reasoning 潛力

報告時可抓的主軸

  • 檢索不只是「取回更多」： 關鍵在於何時檢索 (when)、如何檢索 (how) 以及檢索到什麼程度。
  • 工具介面限制了自主性： 單一粒度的工具（如只提供 vector retrieval）限制了 LLM 在不同推理階段的靈活性。
  • A-RAG 把檢索變成大模型可互動的多粒度決策問題。

研究問題與主要貢獻

A-RAG 核心思考：如何將資訊檢索設計成對 Agent 友善的多粒度互動式介面？

Research Question (核心命題)

Can a language model autonomously choose retrieval strategies across multiple granularities and scale with test-time compute?

★ 貢獻 1：Paradigm Shift

指出 RAG 研究應從靜態的管道組裝 (Static Pipelines) 轉向動態的代理決策架構 (Dynamic Agent-based Systems)。

★ 貢獻 2：A-RAG Framework

設計了層級式檢索介面 (Hierarchical Interfaces)：融合精確 Keyword 匹配、Sentence 層級語意搜尋與 Chunk 逐次讀取。

★ 貢獻 3：Scaling Analysis

首次深入探討並量化分析了 模型規模、最大步數限制與思考深度 (Reasoning Effort) 對 RAG 表現的擴展規律。

  • 本篇核心不是更換更強的外部向量檢索器，而是改進 LLM 與知識庫的互動協定。
  • 實驗著重於多跳問答 (Multi-hop QA)，因為這類問題最需要多輪交叉比對與長鏈推理。

A-RAG 方法架構總覽

整體架構由 Hierarchical Index、Retrieval Tools 以及最簡 Agent Loop 三大部分組成。

設計的核心價值：

不再是一口氣將大量無關 context 塞給模型。A-RAG 透過層級化多粒度介面，允許 Agent 僅提取當前思考所需的高價值 Snippet，並隨後按需讀取完整內容，大幅降低計算冗餘。

Hierarchical Index：三層資訊粒度

A-RAG 將知識庫組織成多層級結構，以支持不同精確度要求的查詢情境。

Keyword-level

特點：免除複雜的線下倒排索引建立。在查詢時直接進行實體或專有名詞精確文本匹配。

Query-time match

Sentence-level

特點：將 Chunk 進一步切分為單句，並計算 Dense Embedding，支持精細語意相似性計算。

Dense sentence vector

Chunk-level

特點：包含 1,000 tokens 左右之完整內容儲存。只有在 Agent 明確判定需要時才會被加載。

Progressive chunk read
  • Sentence-level Embedding 讓 Agent 可以精確定位最相關的核心句子，獲取片段 Snippet 資訊，再藉此評估是否要調用完整 Chunk。
  • Keyword 適合實體人名、型號、代號等絕對精確搜尋，而 Semantic 則適合概念化、同義詞但措辭不同的語意查詢，兩者互補。

Keyword Search：精確詞彙搜尋

利用 Literal Keyword Matching，快速精確地找到包含特定核心實體 (Entity) 的文檔。

概念化 Scoring 計算

Score(chunk, K) ≈ Σ count × len

核心直覺：關鍵字在該 Chunk 中出現次數越多、關鍵字本身字元長度越長（越長代表詞彙越具體），該 Chunk 與當前意圖的相關性評分就越高。

INPUT
Keywords = ["A-RAG", "chunk_read"]
↓
OUTPUT
符合的 parent chunk IDs + 關鍵字前後的簡短片段

*Snippet 僅提取包含命中詞前後的單句，藉此減少大模型 Context 成本。

  • 顯著優勢：對特定專有名詞、數據集名稱、計量數值進行精準查找時效率極高。
  • 低建置成本：論文特別強調避免了 Graph RAG 龐大的線下圖譜建置計算負擔 (Zero offline construction overhead)。

Semantic Search：句子層級語意搜尋

用 Dense Embedding 向量找到語意最相近的特定 Sentence，並快速回溯至其 parent chunk。
Score_sem(sentence, q) = Cosine(v_sentence, v_q)
每個 Chunk 的最終相關性分數，由其內部評分最高的一句話決定。
檢索系統只輸出這些最高分的 Matching Sentences，作為 Snippets。
  • 解決 Keyword Search 找不到，但字面意思語意極為相近的問題（如語意同義轉換）。
  • 相較於對整個 1000-token chunk 計算向量，針對單句（Sentence-level）能更精確定位具體細節，避免核心語意被雜訊稀釋。

Chunk Read：Progressive Information Acquisition

搜尋工具優先回傳短 Snippet，大模型代理在判定有需要時才載入完整 Chunk。

Context Tracker (智慧快取機制)

Agent 歷史對話中讀過的完整 Chunk 會被系統追蹤。當 Agent 多次查詢並命中有重複的 Chunk 時，系統僅回傳提示，不再重複載入全文，避免重複消耗 Token。

Agent Loop：ReAct-like 工具呼叫流程

A-RAG 採用極簡的代理人循環，以純淨隔離出 Hierarchical Index 的真實效用。
  • 單一工具限制：每一步僅呼叫一個 Tool，以防大模型在複雜流程（Multi-tool Orchestration）中產生混亂。
  • 安全熔斷機制：當迭代次數達到最大限制（Max Iterations）仍未回答時，強制命令模型根據當前已搜集到的所有線索整理最佳答覆。
  • 實驗核心：避免花哨的 Agent 架構污染實驗，純粹考驗層級化工具是否能引導 LLM 自然學會有效的檢索策略。
